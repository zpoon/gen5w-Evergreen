# Evergreen (fork of HMG Leafia Plus): notes for Claude

Community tooling for Hyundai/Kia/Genesis **Gen5W** head units (Telechips TCC803x/TCC897x, Android 4.4.2, Dalvik), installed through **NEMESIS** (xwtk/hmg_nemesis, AGPL-3.0). Created by VysseCodes (archived upstream: VysseCodes/HMG-Leafia-Plus); this community fork, **Evergreen** (zpoon/gen5w-Evergreen), is maintained by zpoon (Nick). Project-facing text says Evergreen; technical names stay as they were so existing installs and reports keep working: package id `wireless.carplay.aa`, the Leafia kit (`kits/leafia`, `leafia-kit*.zip`, `LEAFIA/`, `LEAFIA-REPORT.txt`, `LEAFIA-LEVEL`, `LEAFIA-WIFI-CLIENT`), `Leafia:` log tags and the `HMG Leafia Plus` marker `tools/mkmenu.py` looks for. Reference car: 2023 Kia EV6 (CVEV.USA, firmware 260507, with HUD).

## Working conventions

- Root commands on a head unit go through NEMESIS: `adb shell "nemesis root -c '...'"`. `nemesis root <uid> -c` runs as another uid (1000 = system).
- Anything that writes to `/system` ships as a NEMESIS package with a stock checksum gate, a backup, and an uninstall that restores the exact stock bytes.
- Test packages on the mock head unit (below) before anyone runs them on a car, and say which cars a change was tested on.
- Commits: describe the change in plain words. Don't rewrite or force-push shared history without the maintainer's OK.
- `packages/wireless-carplay-aa/NEMESIS.data` uses descriptor `version=1.1` (NEMESIS 1.16). Its `os=` lists `ro.build.product` globs for every supported car and firmware (e.g. `CVEV.USA.*.260507`); keep it in step with `patches/cars` (`tools/check-descriptor.py`, run by `build-package.sh`, fails otherwise; `tools/test-cars.sh` checks that each car's product ids reach its set through `scripts/cars.sh` and that `os=` takes them). Bump `package-version` for each release; the release tag must be `v<package-version>` (on `main`). A beta is tagged `v<package-version>-beta.N` on any branch and published as a pre-release, never the latest; if a beta needs changes, the next beta bumps `package-version`, so no number is used for two different builds.
- No links to Claude chats or sessions in commits, PR descriptions or comments: no `Claude-Session:` trailers and no claude.ai session URLs. A `Co-Authored-By: Claude` line is fine.

## Hard rules

- Gen5W is only in navigation trims; non-navigation trims have a "Display Audio" head unit (e.g. Display Audio Gen2V on the Tucson), unsupported and absent from the update catalogue.
- Only each car's newest firmware for its region is supported (US 260507, and 260903 for the Ioniq 5; Canada 260206, and 260903 for the Ioniq 5; each region has its own builds, so `patches/cars` and `compat.json` match the full region, e.g. `CVEV.USA.`). Korea: a Korean car goes on the list only once its Wi-Fi chip is shown working (kernel log: SDIO card, `Firmware up`). So far that's only the Kia EV6 260902 (issue #11); the K5 Hybrid and Ioniq 5 units checked had no Wi-Fi hardware, so their sets stay off the list. Don't port older firmware; ask the owner to update the head unit. On a known car with other firmware the installer falls back to basic mode and says to update (`MODE_UPDATE`).

- Never flash MICOM, the bootloader, or modem firmware. Never flash firmware meant for another car.
- No sending our own CAN frames without a separate review. Vehicle commands only through the stock services (BCMManager etc.), and each new one gets its own review.
- Never collect or publish per-car secrets: `/data` contents, the telesecurity partition, certificates/keys, account tokens, VIN, serials, SIM/IMEI/phone numbers. Model-level firmware keys only privately, with consent.
- The repo holds **no full manufacturer apps or libraries**. Allowed: hash-only recipes, delta patch sets (`patches/`), checksums, our own code.

## Gotchas learned the hard way

- The AA library patch (from NEMESIS `projection.tbt`) moves the program headers to 0x1c4000, adds a 9th PT_LOAD with self-contained code, and hooks `sendVersionRequest`+0x12, `RdsType_IsValid` and `NavigationStatusEndpoint::routeMessage`+0xe8 (`b.w` into the new code). The new code reaches the library only through a 5-entry relative table at 0x1c4160 (two `navigationNextTurn*` thunks, two unnamed STLport string helpers, the return address). For a build with a different stock library, re-point that table and the hook; if the build inlined a helper, carry a copy of it in the new segment. `tools/port.py --lib-build` takes the result. Check the method first by rebuilding the US patched library from US stock byte for byte.
- **Deodex with `baksmali x -a 18`**, against the car's own framework dir with the full BOOTCLASSPATH order (core, conscrypt, okhttp, core-junit, bouncycastle, ext, framework, framework2, telephony-common, voip-common, mms-common, android.policy, services, apache-xml, webviewchromium, automotive) plus every other framework odex. `-a 19` silently mis-maps instance fields (KitKat libcore Object fields) and skips classes.
- `port.py` stops when a class we changed is on the reference car but not on the new one (renamed or removed): the 260903 navigation app renamed `b/i` (our `projectionRoute()`) to `util/NaviConfig`, and the old port carried the 260507 copy over silently. The `neev23_260903` patches carry their whole result (they read nothing from the source odex), so a 260903 build can be recovered from its `.lpd` to compare with a new car's code. They are rebuilt the same way (`write_nosrc`: header with the stock odex's md5/length, the whole dex as the extra block). The stock APK a manifest md5 needs can be recovered from an installed one: `zipadd` only appends `classes.dex`, so dropping that entry gives back the stock bytes (done for #16 from an owner's port kit taken with Evergreen installed; md5s matched `stock`).
- Abstract Binder stubs implementing in-app interfaces can still deodex with wrong method names; compare against a known-good build before trusting a class.
- System apps: PackageManager only verifies `AndroidManifest.xml`, so stock APK + injected `classes.dex` installs fine; delete the odex and dexopt (`dexopt --preopt apk odex m=y,u=n`).
- Every outgoing SMS on these units needs `android.permission.TMSC_SEND` (Mobis) as well as `SEND_SMS`. Only system-uid callers pass: `nemesis root 1000 -c 'service call isms 5 s16 android s16 <number> i32 -1 s16 <text> i32 0 i32 0'`.
- CarPlay first-connect notice: DiPO looks it up by the phone's Bluetooth address before iAP2 identification, but saved it under the iPhone serial. The bridge build now saves both (`i/e.ev6LastBtId` + `service/aa`).
- CarPlay turn-by-turn maneuver index fix (Isaac Wisdom): `e/u.d(Object)` wrote into a clone of the index array.
- Cluster navigation mode (`responseNaviAliveStatus`, `updateOperationStatus`): on these newer units the car's own navigation shows turn-by-turn without ever sending either (after boot it sends status 0, then only its "ready"/validity message). Stock US/Canada DiPO never runs its cluster start/stop (`i/e.jw()` needs stepofspec >= 999; the turn-by-turn build sets 0, so `DipoService.cn()` runs them on every navigation-owner change). Once phone guidance sent alive + status 1, nothing sent at the end (0, 1, 2 or nothing) brought the cluster back: it spun until the car's navigation re-sent "ready" on its next route (US and Canadian EV6). Status 2 = no map card on SD-card models (Canadian EV6: "Insert SD card to use navigation"; the US EV6 is eMMC). DiPO and GPM now never send either, only turn data (`~/hmg-private/tools/srcfix/apply4.py` + `apply5.py`).
- Speed limit, cameras and traps while a phone guides: the turn-by-turn build muted the car navigation's trap frame (`updateTBTTrapInfoNew`: speed-limit digits, camera types, curve/merge/zone warnings) and HUD camera distance (`updateNaviWarnDist`) along with the turn display, and stock GPM's `updateTBTTrapInfo()` sent the 17-int clear after every maneuver (wipes the speed-limit byte). Under CarPlay the cluster kept a stale sign; under Android Auto it was wiped. Phones carry none of this data. Now the navigation app's mute (`e/a.sendClusterData`, `message/a.d([BI)`) lets trap/camera codes 1, 4, 0x4B, 0x4F through and GPM's clear does nothing (`~/hmg-private/tools/srcfix/apply6.py`). Driver-assist map data (`updateV2*`/`updateV23*`), `updateSCC_HU_Navi_P` and `updateISLAAdd` were never muted.
- CarPlay turn-by-turn symbols (#16, #9): DiPO's `e/u` turns each iAP2 maneuver (type, driving side, junction type, exit angle) into a cluster symbol through a table that matches exact angles only (slight left only at -45, highway exits and change-highway only at 0) and has nothing for off ramp, keep left/right or change highway. A symbol of 0 is never sent (`if-eqz v1` before `updateTBTInfo`), so the cluster and HUD keep the previous instruction and distance. The US "not send by navi" filter is already bypassed in the turn-by-turn build. `u.leafiaFallback` (computed before the stock switch into `u.leafiaFb`, used where the stock result is 0; `~/hmg-private/tools/srcfix/apply8.py`) maps those maneuvers to the symbols GPM sends for the same Android Auto ones: 0x41 straight, 0x42/0x47 slight right/left, 0x43/0x46 right/left, 0x44/0x45 sharp right/left, 0x48/0x49 U-turn, 0x51/0x52 exit right/left, 0x56 exit, 0xac/0xad/0xae ramp straight/right/left. Roundabouts: the stock table has an exact angle per type only (exit 1 at 135, exit 2 at 90, exit 4 at 0 ...; nothing for exit 3, exits 9-19, enter/leave), so CarPlay roundabouts froze the cluster (US Ioniq 5 260507, Apple Maps). `~/hmg-private/tools/srcfix/apply14.py` (after apply8/12) renames apply8's method `leafiaFallback0` and wraps it: where it gives 0, `u.leafiaRbSym` maps junction type 1 or maneuver types 6/7/19/28-46 by exit angle a with GPM's Android Auto ranges (GPM's angle = 180 - a): 0 -> 0x61 (0x60 left-hand traffic), (0,45] 0x61, (45,90] 0x63, (90,135] 0x64, beyond +-135 and type 19 0x66, [-135,-90) 0x67, [-90,-45) 0x69, [-45,0) 0x6a; leaving (type 7) 0x20, 0x21 left-hand traffic. Stock exact matches still win.
- US cluster symbols (#9): stock DiPO drops a list of symbols on US cars (`updateTBTInfo [US] not send by navi`: 0x49, 0x4c, 0x51, 0x52, 0x54, 0x55, 0x57, 0x58, 0x5a, 0x5b, 0xa1, 0xa2, 0xac, 0xad, 0xae, 0xb1, 0xb7, 0xb8, 0xc0 and up); the turn-by-turn build sends them anyway, and the US cluster draws the distance with no arrow (HUD blank) for at least 0xad (seen on a Palisade: keep right, iAP2 type 14, from `leafiaFallback`). On the US path only, `u.leafiaUsSym` (`~/hmg-private/tools/srcfix/apply10.py`, after apply8) maps the ones our builds produce: 0xad/0xae keep/fork right/left and change highway to 0x42/0x47 slight right/left, 0xac to 0x41 straight, 0x51/0x52 exits to 0xa4/0xa5 (stock's highway off ramps), 0xa1/0xa2 on ramps to 0x42/0x47, 0x49 to 0x48. The `mDisplayType[...]` log line shows the symbol after the map. GPM (Android Auto) still sends 0xad/0xae for forks and 0xa1/0xa2 for on ramps on US cars.
- Stock whitelist firewall (US Ioniq 6; init service `iptrules`, about 6 s after power-on): policy DROP, `WLIST_IN` sends each interface to its own chain; `wlan0` gets only DNS, DHCP and Bonjour, the CarPlay ports (5000-5001, 5020, 6000-6003, 6011, 6020, 6030, 7000, TCP+UDP, either way) only `ncm0` (wired). So wireless CarPlay finds the car and is then dropped; iPhones use link-local IPv6 for it. Service `svc/hotspot-firewall.sh` (only when `WLIST_IN` exists) puts its chain `EVG_HOTSPOT` first in INPUT for `wlan0` from 192.168.0.0/24 and fe80::/10 (IPv6 also ICMPv6), the same ports either way plus TCP/UDP 40515 (wireless Android Auto: GPM's `WirelessExplorer` sends the phone the hotspot address and `setPort(0x9e43)`, and the phone connects in); memory only, checked every 10 s and put back after the stock firewall (re)loads; `preun.sh` runs it with `remove`. Test: `tools/test-hotspot-firewall.sh` (stub iptables). The same fix as HMG-API's `"network"` keeper. Confirmed on a US Ioniq 6 (wireless CarPlay and Android Auto).
- CarPlay picture freeze (#26): the CarPlay library decodes the screen stream itself and reports a stalled decoder to DiPO's `telechips/CarPlayService` (`onNotifyDecodeFailure(int)`: 1 no output, 2 sequence header, 3 black screen, 0 a reset; `onScreenTimeout()`: no screen data for 10 s), which only logs it; nothing calls `forceKeyFrame()`, so the picture stays frozen (audio goes on) until CarPlay is left and opened again. `telechips/LeafiaKeyframe` (`~/hmg-private/tools/srcfix/apply11.py` + `apply11-LeafiaKeyframe.smali`, on the turn-by-turn and bridge DiPO builds) is called at the start of both and asks for a key frame on its own thread, at most once every 2 s; logs `Leafia: CarPlay picture: key frame asked for after ...`. After HMG-API's wireless mod (`dipo/Keyframes`, its PR #16, a 2-hour US EV6 drive with no freeze); its periodic key frame and its reconnect watchdog are not carried over.
- CarPlay screen log and opt-in second recovery step: `telechips/LeafiaScreen` (`~/hmg-private/tools/srcfix/apply17.py`, source `apply17-LeafiaScreen.java`, after apply11/16), called first in `CarPlayService.onScreenStarted/onScreenStopped/onScreenTimeout`, always logs `Leafia: CarPlay screen started|stopped|timeout` (and "started, N ms after the timeout"), so a drive log shows whether apply11's key frame brings the picture back. With `EVERGREEN-SCREEN-RECOVER` on the install drive (flag `/data/nemesis/wireless.carplay.aa.screenrecover`, `opt_flag` in `scripts/common.sh`; mock `MOCK_OPT=...`): if the screen hasn't started again 4 s after a timeout while CarPlay is shown, `changeModeBorrowScreen(UserInitiated, UserInitiated, "evergreen-recover")` and `changeModeUnborrowScreen` 1.5 s later, once per stall, so the phone restarts its video. That calls CarPlayService directly, past DiPO's resource manager (`e/r`, which keeps its own borrow ids), so how DiPO and the phone react is unknown; from KSubedi's Ultimate Wireless Projection fork, where it isn't proven on a car either. Off by default until a car shows it helps.

## Kia Connect (research summary, read-only)

Telematics lives in `HKMC_TAppService` (system uid). Remote commands arrive over MQTT (`mqtt_mosquitto`, a libmosquitto binder wrapper; MQTT 5; topics and host provisioned via the service hub) or a wake-up SMS that makes the unit call back over HTTPS. Commands execute through `BCMManager`/`HEVManager` -> automotive-service -> `micomd` (`/dev/ttyTCC2`) -> MICOM -> CAN. Modem: Qualcomm over USB (`/dev/ttyACM0` AT, `/dev/qcqmi0` data), Verizon (US). Status is reported as VSS paths. Planned direction: a read-only Home Assistant status bridge first, then wake-by-own-SMS testing, then reviewed commands one at a time through the stock services.
